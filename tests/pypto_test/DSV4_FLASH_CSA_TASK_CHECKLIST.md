## 1. 最终交付与验收合同

### 1.1 目标

1. 正式 W8A8 模型的 PTO 接入功能正确，支持当前声明的 decode、padding 和 ACL Graph 场景。
2. 保留精度版、性能版两个入口；共用适配及数值中性实现，明确隔离算术差异。
3. 精度版尽力对齐 Native 的规约规则、量化顺序和舍入；不把完全 bit 一致作为无条件目标。
4. 性能版允许采用 pypto-lib 或 Native 上游已有的精度策略，先看性能收益；
   保留方案仍须独立通过逐元素、状态和整模型验收。
5. 最终 PTO 整模型表现必须明确优于 Native，且性能版
   **HC_pre → norm → CSA → HC_post 完整设备区间 <750 μs**。
   原单卡泳道 ≤725 μs 仅为优化参考，不再作为最终验收线。
6. 四张目标权重 `wq_a / wq_b / wo_a / wo_b` 的 NZ 都继续推进；
   编译限制须先在算子侧寻找解法，未实现不能写成完成。
7. mode=1、mode=2 均评估后选定性能更好的主口径；ND 独立实现与回归入口长期保留。
8. 性能版保留一套当前实现，长短上下文、batch及工作量策略在PTO算子内部按实际输入选择，
   不按测试档位切换历史源码版本。阶段对比使用同一套算子源码的实测结果；
   旧版数据可以用于优化过程对照，不能仅凭计算分支未变就代替当前版本实测。

**当前执行优先级（2026-09-27 用户最新调整）**：先在 CSA 外用现有 Torch API 将 Indexer cache
拆成连续 key/scale，CSA 内直接消费并更新，CSA 后只写回当前 slot；单列拆分、本体、写回及完整路径耗时。
先确认本体能否稳定获益，再决定是否推进分配时分离。七档v4/v7基线已齐，
新候选只补受影响的档位；Score 的块分配与排队长尾仍为待解决项，
不把正常窗口或中位数改善当作阶段完成。精度版算术保持原口径，当前不改分配器。
此前精度版迁移、精度复查及六档对比的有效证据继续保留；它们不自动覆盖这次新候选。
精度检查仍先单卡，再真实权重 16 卡。
精度版保留当前对齐 Native 的算术方式，不能为了共用代码引入性能版的算术策略。已发现差异保留必要记录，
不把“暂不展开诊断”标成逐元素验收通过。功能越界、漏写等问题仍须修复。

750 μs 的确认口径：B16、S6、TP1、EP/DP16、H8192、FULL_DECODE_ONLY；
统计各 CSA 层稳态完整设备区间的中位数，并报告 p95、rank/层分布。
该区间含内部间隙与必要适配，不用各 kernel 耗时相加代替。
最终主对照两侧使用相同 mode，各测 mode=1/2 后选定主口径，保留另一档结果。

这是新增泛化对比，不替换原 B16/H8192 的 <750 μs 目标，也不据此恢复无关的历史测试矩阵。
单卡主计时按同一步第二个 CSA 层：PTO 复用前层已经生成的 compact metadata，
Native 保留实际逐层执行路径。首层 metadata 生产成本单独记录，不混入主结果；
仍覆盖 HC_pre 到 HC_post 全区间，最终整模型继续报告各层分布。

### 1.2 功能错误与精度权衡分别处理

| 类型 | 判据与处理 |
| --- | --- |
| 功能错误 | 错误布局/stride/offset、越界、漏写、错误 metadata、陈旧状态、未声明回退、非有限值、错误同步均必须修复，不得靠容差掩盖 |
| 精度版算术 | 对齐 Native 规约、量化顺序及舍入；逐元素报告差异，区分固定实现差异与运行间波动 |
| 性能版算术 | 可以采用 pypto-lib 或 Native 上游策略；逐项注明与精度版的差异、适用范围和误差证据 |
| 整模型 | 必须逐 token 一致，同时检查真实 DSpark 草稿数、接受数/长度及层级误差 |
| metadata 与保护区 | 长度、页号、slot、掩码等整数/索引逐元素精确一致；不得写的区域保持不变 |
| 浮点 cache/state | 每种状态单独明确有效范围、atol/rtol、误差统计及参考来源，未定标准不能 PASS |
| 量化 INT8 / Top-K | 允许符合明确量化/选择/tie 规则的差异，前提是逐元素误差受控、逐 token 和 DSpark 统计一致；规则须在验收前明确，不把它们与 metadata 索引混为一类 |
| 非确定性 | 先量同输入重复执行的逐元素误差，再比较实现之间的误差；不能以 mean/absmax 相同替代数值验收 |

现有 BF16 `atol=1e-2, rtol=1e-2` 仅是旧单层输出标准的参考，
不得直接套用 mHC 残差流、所有中间量或全部浮点状态。
门槛须先与对象和算法对应，再用于新实验；失败后不得自动放宽。

### 8.1 六档实测（两侧 `weight_nz_mode=1`，池化基线，§160）

| 档位 | Native（n, σ） | PTO | ratio |
| --- | ---: | ---: | ---: |
| 8K/B24 | 1160.2（7, 1.1%） | 1136.8 | **0.980** |
| 128K/B4 | 865.2（6, 1.1%） | 859.8 | **0.994** |
| 8K/B32 | 1299.1（7, 1.2%） | 1309.0 | 1.008 |

基线必须池化：Native 侧代码在优化周期里不变，其同档位耗时是固定量，单次基线的偏差
可达 4σ（8K/B40 的运行间极差 9.9%）。判断 PTO 改动有效性时比较 **PTO 绝对时间**，
不要比较 ratio。

### 8.2 成本结构：差距全在"随历史增长"的那一段（§155、§156）

固定 B16 只变历史：h=8192 时 Native 923.1 / PTO 880.8（**PTO 快 4.6%**）；
h=131072 时 Native 1342.5 / PTO 1806.1。8K→128K Native 只涨 419.4 µs，PTO 涨 925.3 µs
（2.2 倍）。**PTO 的固定部分优于 Native，差距全部在历史相关的 indexer + 按键注意力。**

Native 逐算子实测（`--profile`，128K/B16）：`VllmQuantLightningIndexer` 366.4 µs、
`SparseAttnSharedkv` 172.3、`Compressor` 141.4(x2)、`aclnnQuantMatmulWeightNz` 108.3(x3)。
8K/B40 时融合 indexer 只有 91.6 µs。

### 8.3 ≤0.700 为何不可达（§155）

128K/B16 的预算是 0.7 × 1319.4 = 923.6 µs，而 PTO 的固定部分约 880.8 µs、占 94%。
即使把 indexer 换成 Native 的 366.4 µs，总计约 1247 µs、ratio 0.93。要达标 PTO 的
历史部分必须 ≤ 43 µs，即比 Native 手调融合算子快 8 倍以上。**这是算术，不是优化力度问题。**

### 8.4 已封闭的方向（实测负收益或硬件报错，勿重做）

| 方向 | 结果 | 小节 |
| --- | --- | --- |
| `REPACK_WORKERS` 48→192 | **采纳**，128K/B16 −8.5%，数值中性已验证 | §147、§148 |
| score 向量链（ReLU/加权/scale） | 去掉 60% 算子对整体无影响，score 不是向量受限 | §151 |
| score 的 KV gather 减半 | 更慢（+1.1% / +6.9%） | §151 |
| 两 query 合批抬高 Cube M | M=128/N=256 报 Vec 197632 > 188416；降 stage 只省 256 B；N=192 可编译但块数/L0C 与现状相同、无理据 | §153、§154 |
| `SCORE_TILE` 上下调 | 448/512 报 Vec 超限；320/256 实测 +19.5%/+7.6% | §145、§154 |
| `TOPK_CANDIDATES_PER_LEAF` 上下调 | 16384 报 Vec 262144 超限；4096 报 source extent 8192 | §145 |
| `TOPK_SCORE_WORKERS` / `TOPK_QUERY_WORKERS` 加大 | 全部更慢（+0.2%~+4.6%） | §149 |
| `QK_PRE_LAUNCH` 2→3 | 报 Mat buffer 606208 > 524288（L1 512 KiB） | §154 |

### 8.5 唯一还有量级的方向，需要部署侧决定

**增量 repack**：每步只重搬新追加的页，收益是探针实测的约 350 µs（128K/B16 可到约 1.09）。
前提两条，都超出算子内部：

1. 缓冲尺寸要从 `MAX_SEQ_LEN = M.max_position_embeddings`（生产 config 是 **1M**）
   改成部署的 `max_model_len`，否则 21 个 ratio-4 层合计需 10.5~26 GiB；
2. 即便改成 128K 定尺，仍需 **1.32 GiB（B16）~3.30 GiB（B40）** 额外显存，
   等量减少 KV cache 容量。

缓冲只能按 `(槽位 × 每槽最大行数)` 索引——按物理块索引会丢掉"同请求逻辑页连续"，
那正是 repack 存在的理由。实现上判据必须做在 device 上（aclgraph 重放不进 Python），
可证明正确的做法是持久化每槽 block table 整行逐步比对：整行一致且 `seq_len` 只增长
⇒ 旧页仍有效，从 `old_len // BLOCK_SIZE` 那页起重搬。详见 §158、§159。
