# 2026-10-20：等待代表档结果期间的 Attention 供数复核

本文只使用已完成的 B16/B28 供数诊断及正式源码，没有新跑设备，没有修改
候选或正式算子。原始数据在两份 `supply_h131072_b*/phase_clock/` 中。

## 已有计时能说明什么

| 项目 | 128K/B16 | 128K/B28 |
| --- | ---: | ---: |
| AIC 等 KV 的 Scalar 包围区间中位数（μs） | 101.36 | 186.50 |
| AIV 包围完整 MGATHER 的累计区间中位数（μs） | 26.15 | 42.82 |
| 每角色有效 Attention 块数 | 20 | 35 |
| 每 AIV 的 MGATHER 次数 | 16 | 28 |

这些计时有探针开销且相互重叠。MGATHER 包围区间含内部同步，不是独占
MTE2 时间；不能从第一行减去第二行，断言剩余部分都是 Vector 数学，
也不能把两者当作删掉某段代码就能获得的收益。

同次全核阶段端点显示，B16 两 AIV 的 Attention 完成时间落在
674.86～693.74 μs，B28 为 1047.48～1090.02 μs。这是各自诊断调用的
共同时间轴，不是完整无插桩 L1，也不能与另一轮结果拼接性能收益。
B28 每组同为 7 个 query、35 个有效块，仍有约 42.54 μs 的完成时间差；
因此不能仅凭分配数量相等就认定所有核完全同步推进，也不能据此认定
存在硬件慢核。依赖就绪时间、地址访问、内部等待和探针均可能影响端点。

## 源码中的实际供数链

正式 `attention_stream_stages.py` 的每条 AIV 同时承担：

1. 当前块的 64 行 KV 采集、写出；
2. 前一块的 32 头 softmax，产出 BF16 probability；
3. 前三拍块的在线 m/l/oi 归并；
4. query 最后一块的归一化、逆 RoPE、BF16 与 packed 输出。

因此下一次 KV 发布受整条 AIV 迭代影响。AIC 等待 KV 不是单独的
“随机采集函数慢了多少”。小 token 区间发布 KV 之前还执行上一块
softmax；大 token 区间先获取上一块 SCORE 再发布 KV，随后执行
softmax。这些顺序同时约束三槽复用，不能只按是否看起来能提前通知改动。

两个 AIV 各处理半份 KV 和半份 heads。若改成一条专做 gather、另一条
专做全部 softmax/merge，后者数学工作量会增加，事件、槽生命周期与 UB
峰值也会变化。当前证据不支持直接这样分工，更不能将其宣称为已确定收益。

## 当前决定

先收齐整块 Key 准备候选的 B16/B28 三方五窗完整结果，按用户确认的
“一档至少净省 20 μs，另一档无明确退步”决定是否扩档。Attention 的这些
证据作为下一候选依据保留；不为排队期间找事情做而重复提交已有探针，
不改真机同步、不放宽数值门槛。若转向 Attention，仍须指出具体缩短的
依赖链，并与已有提前 KV、PV 先行、直接 L1、32KiB 缓冲负例区分。
