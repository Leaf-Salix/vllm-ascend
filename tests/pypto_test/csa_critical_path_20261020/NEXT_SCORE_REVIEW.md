# 下一步只读结论：不能直接重跑旧M192双Acc

Attention独立64KiB/四半段状态已完整正确但无净收益，停止该方向。
本文件只是后续设计审查，不是新算子实现、CPU通过或设备收益记录。

## 已核对的旧负例

历史csa_multishape_spmd_20261016/indexer_score_pingpong.py把G6的QK分成
两个M192/N64。它已证明两份48KiB Acc同时存活，并完成真实精确检查，
旧完整L1中位968.92μs，对照当轮多task904.72μs，没有采用。
不能把“两份QK Acc能放下”当成新发现，再原样重跑。

旧源每半组只保留三个query的系数，分别WS并各做一次GM写回；每1024
候选32次WS写回。它先发QK0、上一面板WS1、QK1，然后才FIX当前QK0，
因此双Acc存在不代表当前FIX0与QK1有预期重叠。旧源码还依赖冻结T96
入口，不是可迁入ops的目标态动态实现。

## 有区别才值得继续的候选条件

可以在当前源级动态G6/N64区间研究：

1. 用两份明确独立的48KiB QK Acc，第一份立即FIX，再发第二份QK；
   当前两份FIX与原上一面板WS能否重叠，要核对最终地址和set/wait事件。
2. 保留原16行、六query的系数布局，将WS的K384拆为0..191、192..383
   两段累加到同一4KiB Acc，最后一次写出原六行，不做两个三行STORE。
   K段顺序相同，但FP32归约的实际舍入仍必须用完整冻结精确门槛验证。
3. 预计Left为48KiB query加12KiB系数，Right为两份8KiB Key加两份24KiB
   WS，Acc为96KiB QK加4KiB WS。理论上不超限，但CPU必须确认真实
   分配、共存及必要同步，不能把这些容量加法当成已经可用。
4. 只在原G6/N64资源区间编译选择，原G2及其它组合保留；组数、叶计划、
   真实长度、页保护、尾query安全填充、Top-K、1024交接与FFTS均动态保留。
   使用当前精确INT8 L1范围工具链，不采用旧冻结body或B16/S6白名单。

潜在收益来自较早FIX和每面板一次WS写回，并非仅仅缩小M。相反，QK、
FIX与WS的指令数增加可能继续抵消收益。先证明区别在实际代码中成立，
否则不上卡；精确或20μs/另一档无退步门槛不通过就结束，不扫更多tile。
未量出局部瓶颈占比，因此不承诺可省多少微秒或已接近最终30%目标。
