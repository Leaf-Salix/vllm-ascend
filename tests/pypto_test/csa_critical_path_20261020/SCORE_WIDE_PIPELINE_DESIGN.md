# N128宽面板：以WS覆盖同QK Acc的FIX等待

## 范围、历史负例与本次区别

参考为当前正式13259f92/source_after_score_split；此前KV核分配候选已终态
无收益并结束。当前全72角色诊断显示B28 Score仍为较大生产段，AIV累计
READY约113.09μs、AIC ACK约31.77μs，二者含探针，不是可直接省掉的时间。

旧静态indexer_n128.py已测试过M192/N128并回退，不能原样再跑。源码显示
它在当前QK之后先执行另一个WS再发当前FIX，两个三query分别STORE；当时
也没有当前动态前段、Score早FIX/六行合并写回及精确L1范围工具链。

本次在已经采用的N64双48KiB QK Acc基础上，只改私有Cube helper为N128：
一份96KiB QK Acc串行处理两半，利用独立8KiB WS Acc执行上一面板工作，
在当前FIX发出后、下一半QK复用Acc前插入WS。保留六行完整系数K192+192
和一次六行STORE。潜在收益来自面板批次数减半及FIX等待覆盖；损失是
两个QK共用Acc、Key不再提前到L0、首面板无前面板WS。不能只数指令就认定加速。

同步协议复核中没有获得可安全泛化删除发布/获取缓存维护的新依据，因此
本轮不做删fence/cacheinvalid或退避参数扫描。另发现主压缩自动L0切分有
重复Left搬运，但其阶段窗口较小，保留作后备，没有实现或当组件bug提交。

## 数据与资源合同

- 当前QK为M192/N128/K128，两半仍为各三个query；每个有效点积的K顺序不变。
- WS仍是完整16行系数的K0..191、192..383两次顺序累计；每query的非零64项
  只位于一个半区，沿已采用版的系数证明。N扩大不改变每个列的数学顺序。
- Left为两份24KiB Query及两份6KiB系数，共60KiB；Right在稳态为Key16KiB
  和一份WS48KiB。先完成WS0对Right的读取，再装WS1，不同时保持两个48KiB。
- QK Acc[0,98304)、WS Acc[98304,106496)理论共104KiB，实际地址以下述审计为准。
- 每1024列由16个N64面板改成8个N128面板；双槽READY/ACK、leaf drain、
  页表/物理页/尾query保护、group/leaf/Top-K/score缓冲布局均保持。
- T/B/长度/位置/页表仍动态。候选只替换原SPLIT_SCORE_ROWS区间，其他走原helper。

本候选公共policy.QK_PANEL=64仅用于沿用原G6区间选择条件，**实际私有Cube
N=128**，由WIDE_QK_PANEL_COLS明确命名；私有Key预取固定L1一面板、L0预取
关闭。报告必须同时保留这点，不能把候选叫N64。若真机满足采用门槛，正式
接入时应整理策略描述/参数，再核对等价性；目前不更改正式源。
