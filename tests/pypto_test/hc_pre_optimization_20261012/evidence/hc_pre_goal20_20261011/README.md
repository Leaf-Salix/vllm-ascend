目标与口径：全部十四个 B/S 场景均纳入设计，观察 B16/S6 完整 HC_pre
真实 L1 incore 首尾低于 20 μs。计入算子内部空隙，排除外部编排和调度首尾。
用户已取消旧全档 ABBA 复测；本目录不续跑、不发布该轮结果。

正式 `vllm_ascend/ops/pypto/hc_pre.py` 当前对应 `adopted_l0_interleave_exact96.py`：
小档M32/K1536使用有效K512轮数、双槽供数、显式同一Acc与K256 L0双缓冲，
RMS复用输入且保持11份部分和；保留既有中大档供数/混合和T96紧凑Sinkhorn。
T96紧凑Sinkhorn已删除冗余常量计算；T96 L0使用显式交错；最新清单为 `adoption_l0_interleave_exact96.json`。
完整20轮不变，20μs目标仍未完成。
`baseline_merged.py` 是开始新目标时的独立源码快照。

## 初始候选（历史记录，以最新采用清单为准）

- `stage1_selective_v1.py`：保留小中档较少 K 分段，按规格选择 M/K。
  流式分支每个逻辑 K 段内累加 RMS，复用已经加宽的输入；GM 中只留八份 RMS。
  该重分组可能改变 FP32 舍入，尚未通过设备验收。
- `stage1_pipeline_v1.py`：在上项基础上，将流式供数缩为 K512，申请两级核内流水。
  T80/96 使用 M32，T100～144 使用 M48，T168 使用 M32；跨核交接仍为两个槽。
  生成代码确认 AIV 先加载两块不同 UB 地址的输入，AIC 先加载两块不同 L1
  地址的权重；消费顺序是 pop→matmul→pop→matmul。
  `build_stage1_pipeline_v1/report.json` 为 COMPILED，未做设备测试。
- `scheduling_plan.json`：十四档的静态任务分配。24/48 是当前 A3 的任务数分析，
  算子启动核组数仍来自 `available_cluster_count()`。逻辑任务数相同不代表耗时相同；
  例如 T100 按 M48 补至144行，补齐代价须纳入后续取舍，不能仅看24个任务。

两份候选保留当前第二阶段的 48 AIV 分工、完整20轮 Sinkhorn、原有精度门禁、
同一动态 T 入口与三个输出。尚无新性能收益结论，不能视为20 μs目标已经完成。

## HF32 模式隔离诊断

Native 源码 `hc_pre_cube_compute.h` 在 Mmad 前调用 `SetHF32Mode(1)`、
`SetHF32TransMode(1)`。本环境 CANN 的 `kernel_macros.h`、`kernel_reg.h`
将两项映射为 CTRL[46]/CTRL[47]。当前 PTO-ISA 的 `Tile.SetMadTF32Mode`
也提供同样两位设置；但当前 PyPTO Tensor/Tile matmul 接口没有公开相应参数。

`hf32_diagnostic.py` 只在自身进程中修饰 HC_pre AIC wrapper：保存 CTRL，
设置两位，调用原生成函数，恢复 CTRL。PyPTO/Simpler/PTOAS/PTO-ISA 仓库文件
不修改，正式入口不引用该脚本。默认只允许 `--build-only`；设备诊断需显式
指定 `--device-diagnostic`，并由 task-submit 分配设备。

`hf32_build_audit.json` 与 `build_hf32/report.json` 确认五个分支均已编译。
这不是原生 PyPTO API 的优化交付，也未证明 HF32 的精度或耗时收益。
本机 `llvm-objdump` 对 A3 指令仅输出 `<not available>`；保存的
`hf32_exact96.disasm.txt` 不作为控制寄存器指令已执行的证据。
正式接入需要编译接口能表达模式与作用域，不能永久靠测试脚本替换生成代码。
