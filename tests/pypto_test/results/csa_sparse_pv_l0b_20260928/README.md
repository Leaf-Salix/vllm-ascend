# Sparse PV：对齐最新AscendC的L0B双缓冲

基线算子d1f170ff；候选从a66255ea独立工作树派生，两者生产源码相同，仅候选修改性能版Sparse的PV读取顺序。
候选工作树`.cache/csa-sparse-pv-l0b-a66255ea`，冻结差异见[candidate.patch](candidate.patch)。
主工作树已有的wo_a布局修改不属于本项，也没有混入两侧设备测试。

## 来源和具体差异

ops-transformer b5b33e14的
`attention/sparse_flash_mla/op_kernel/arch22/sparse_flash_mla_csa_block_cube.h`：
`InitBuffers`为L0B分配2×32KiB；`ComputeMm2`用`abL0BufIter % 2`轮转，配合MTE1/M事件。
当前PTO已经采用N128/K128和两份L0C，QK也已经是K128双缓冲，不将这些已实现部分再计为新收益。

基线生成C++的PV四份Right tile均分配到L0B偏移0；在下一次TEXTRACT之前等待上一MMAD完成，
所以“两个Acc同时存活”并不等于输入也双缓冲。本候选先保留当前和下一个N128 Right tile，
之后在计算当前块时搬运后一个块；保留两份Acc与原来的N块输出顺序。

完整CPU lowering、PTOAS、CCE和AICPU链接已通过。生成代码确认Right偏移0/32768交替，
每块仍是同一BF16 K128矩阵乘，原先的L0C双缓冲保留。
QK/PV共享的三个完整KV L1块、预发深度2、五块softmax、跨query流水、任务数及调度标志均未改。
与pypto-lib的差异仍包括Native cache的分页读取、当前五块流水和单独合并；本项只处理核内PV搬运等待。

128K为148.29/143.20/142.63/145.81→144.19/145.47/139.33/145.11。
这些是先后独立采集，并非同一调用的配对样本；两个分布均重叠。
未修改的merge_norm也由25.85→23.83、24.46→23.97μs，不能将所有下游变化直接归给PV双缓冲。
Native控制均值短档939.95→938.73、长档1308.58→1323.73；原样保留，不归一化抵消PTO回退。
本次全部DFX窗口Sparse均为24个AIC各一块，没有复现同核两块，不因此宣称旧尾部消失。

两档八类PTO状态均逐bit一致，保护区、自重放、图计时状态及候选A→B→A通过。
这说明候选在本次范围内数值中性，不证明所有档位或EP16通过。
**暂不并入性能版**：尚不足以把1%～2%的核内平均下降认定为明确收益；长档完整均值/P95小幅上升。
结束本项扩测，保留可复现补丁及证据；后续只有新的等待/搬运证据才重新评估。
不因L0B双缓冲生成正确就自动宣称性能改善，也不因本候选未通过否定AscendC的整体流水设计。
