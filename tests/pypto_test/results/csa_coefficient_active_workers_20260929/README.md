# 系数生成：只取消无计算迭代的worker

状态：已准备私有候选，生产/测试两根依赖图解析通过，尚未完整编译或设备执行，不合入生产。
等待当前七档矩阵收齐，再根据长档关键路径决定设备对照；不与阶段基线混测。

当前c93ec723的`indexer_head_coefficients`固定48个worker，内部按stride=48分配query组。
长B4/B8/B16/B24已改为S6，每组对应一个请求，实际仅4/8/16/24个worker有循环迭代。
短B24/B40是S6，实际24/40个；短B32双query共96组，48个worker都有工作。

候选仅将提交数改为`min(48, query_count // query_group_size)`，内部stride仍保持48。
不把工作合到其他worker，不改FP16舍入/乘法/写回、依赖、early_resolve、Score同步或cache布局。
新七档提交数理论为4/8/16/24、24/48/40；完整编译和DFX仍需确认。

这与验证日志§223的失败试验不同：当时是8K/B16双query，共48个有工作的组，
提交上限改24且stride也改24，令每worker承担两组；该路径本体和P95退化后撤回。
本候选在48个有工作组时仍提交48个，不复用旧48→24的负载合并策略。

## 当前证据与检验重点

最新七档B4/B8的四个level-4窗口已用Simpler官方时钟域解析器检查：
Score经常在系数任务FIN之前已派发，不能把其全部等待叫作队列延迟。
B4系数end→FIN为3.520–13.480μs，B8为5.580–14.000μs；
其中包含完成通知/依赖处理等时间，尚不能证明空任务是唯一原因。
长B16的四个窗口中，window_0/1最后完成的是`idx_kv_scale_commit`，
比系数核分别晚7.620/7.640μs；window_2/3则由系数核最后完成。
因此删空worker可能只改善部分窗口，必须看Score实际开始及完整CSA，不能预先按任务数换算收益。
scale写回当前对原Native页的64字节scale区域执行读改写，串行用于避免相邻更新互相覆盖；
没有证明页面写入所有权前不能直接并行或取消这条依赖。
Native在融合QLI内生成系数；最新pypto-lib decode没有当前第二次Cube所需的独立系数任务。
因此这是当前PTO额外任务的派发优化，不声称直接照搬上游任务图。

若进入设备对照，先128K/B16和8K/B24；保留后再覆盖实际受影响的B4/B8等。
比较真实编译PTO的20次均值、P95/max及独立DFX中的系数最后结束/FIN、Score首次开始，
按长短8:2判断完整CSA；系数核时均值会因删除空worker改变采样总体，不直接据其涨跌判核内收益。
八类跨版本状态、图重放和保护区沿用已有检查，不追加整模型或全矩阵精度测试。
