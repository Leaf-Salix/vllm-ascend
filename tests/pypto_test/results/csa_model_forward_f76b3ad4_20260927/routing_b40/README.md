## 1. 满档不保证相同步的输入构成相同

两侧81920个输出token一致，16rank的DSpark统计一致，但48组rank/step中仅6组的完整输入相同。
异步入场使部分请求先推进一步；例如rank0的第8个满档step，Native有12个请求起始position=8241，PTO有13个。
因此不能把原始接收负载差异全部归因于PTO算术，也不能以“都满B40”证明MoE工作量完全相同。

后续基准改为公开API `sleep(level=0, mode="keep") → enqueue → DP CPU barrier → wake_up(tags=["scheduling"])`，
整批入队后再开始调度；level0不卸载权重、不清空cache。正式forward额外保存已有CPU请求位置，
不在计时区间加入设备复制或同步。旧数据保留实际口径，不与修改入场方式后的新对照混算。

## 2. 对输入相同的请求，PTO仍改变后续专家选择

在相同rank/step中，以整个请求S6的token与position都一致为条件，配对1860/1920组请求，覆盖96.875%。
仅对这些请求统计专家选择；以下数值为43层×3步的均值。

| 由配对请求产生的专家工作量 | Native | PTO | 变化 |
| --- | ---: | ---: | ---: |
| 全EP组活跃专家数 | 92.17 | 123.01 | +33.46% |
| 每层步最多活跃专家的rank，其专家数 | 9.12 | 11.07 | +21.43% |
| 每层步接收token最多的rank，其token数 | 3428.14 | 3396.61 | −0.92% |

全量global expert ID按每rank16个专家重建的计数，与全部4128组实际MC2逐专家计数精确相同；
因此上述expert→rank映射有实际dispatch数据支持。

层0/1/2的配对请求专家集合完全一致；层3开始出现差异，层10/20/42集合不同的token分别7119/9659/7962，
各层分母11160。相同最终token并不意味着中间MoE工作量相同。
活跃专家更多可能增加权重读取和小分组矩阵计算，是需要关注的整网代价；
**没有据此把forward差额精确换算成FFN耗时，也没有证明其唯一成因是atomic_add或某一舍入操作**。
原始整rank负载还含60组未配对请求，只作为观测保留。
