## 与Native及pypto-lib的对照

Native `quant_lightning_indexer_service_cube.h` 的 `ProcessQk` 每次按 `S2_BASIC_BLOCK_L0=128`
调用 `KeyNd2NzForPA`，按物理页将key搬入L1，之后执行当前QK并与上一块WS交错；
key L1使用双缓冲，缓冲可在MTE1取走数据后复用。不是先把全部2048候选搬完再开始Cube。

上一轮PTO直读版先搬完1024/768候选（32/24页），然后依次做128列QK/WS。
本轮将key加载移进已有128列panel循环，每panel四页，直接L1转L0B，保留上一panel的FP16 Score及WS顺序。
编译产物确认TLOAD与TMATMUL交错，L1不再保留整块1024/768 key；
并非手写与Native完全相同的硬件双缓冲，实际同步/重叠程度仍由PTOAS生成与设备计时决定。

最新pypto-lib2164563的buffered Score仍按完整768候选加载，之后整块matmul，
且只在large-batch/long-history分支选择该路径，head规约方式也与当前性能版不同。
本轮采用Native的细粒度加载策略，因为当前已使用N128 FP16/Cube规约和双query复用，
照搬上游整块加载会保留上一轮已测出的长档核内瓶颈。

Native cache布局、分配、页表、生命周期、精度版与工具链均不改；
PTO内部root/cache改动沿用上一轮候选，所有key按任意物理页表定位，尾页夹到最后有效页再由既有mask筛除。
