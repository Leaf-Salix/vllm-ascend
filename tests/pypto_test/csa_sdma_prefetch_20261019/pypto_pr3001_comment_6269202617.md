在将本 PR 与 hw-native-sys/simpler#2583 配套用于 A3 的完整 MIX SPMD 时，发现一个需要补测的多 AIV SDMA 通道绑定问题。以下区分已测事实和原因判断，**暂不认定是本 PR 新引入的回归**。

### 环境与范围

- A3，CANN 9.2.0-beta.2，torch 2.10.0 / torch_npu 2.10.0.post2。
- 迁入本 PR head `ed612fbdb7e321013fc4324bd2a6febd86df2234` 及 Simpler PR head `0b34c256ff9c027f1afaf83c9c71eadda8ec2daf`，独立重建 runtime / binding / PyPTO adapter。
- 本地 CSA 工具链有既有编译修复和参数扩容，因此这不是未经改动的 PR head 单独测试；SDMA/PTO-ISA 实现保持所迁入版本。
- 原 Simpler kernel-mode SDMA 测试在 TMR、HBG 各 **5 passed**，每个场景按原测试 100 轮。初始化日志显示 **48/48 channels warmed**。
- 扩展用例：`with pl.spmd(24, sync_start=True)`，cluster 内一个 AIC 函数和一个 `split_aiv=True` 的 AIV 函数；生成编排已检查为 `MixedKernels{0, 1, 1}`，即 24 AIC + 48 AIV。不是少启动了一半 Vector 的测试配置。

### 已确认的现象

每条 AIV 的核心操作：

```python
pl.func_attr({"split_aiv": True})
worker = pl.tile.get_block_idx() * 2 + pl.tile.get_subblock_idx()
# region 是该 worker 对应的 4 KiB 连续 GM 区域
ctx = pl.prefetch.make_context()
event = pl.prefetch.async_prefetch(region, ctx)
session = pl.prefetch.session(ctx)
if pl.prefetch.wait(event, session):
    # 读取该行并加 1，写回输出；每个 worker 独占 64 字节完成标记
    ...
```

先做 eager，再用同一 context 重复调用/图重放并更新输入。TMR、HBG 的正常 48-AIV 版本均见整行未写回。随后在**生成 C++ 的 Wait 后**采集事件状态，避免由 Python cast 的行为判断 Wait 返回值：

```cpp
bool completed = event.Wait(session);
// 各 worker 独占 64-byte GM 行，写后 dcci + dsb
diag[3] = static_cast<int32_t>(event.valid());
diag[4] = static_cast<int32_t>(session.valid);
diag[5] = static_cast<int32_t>(completed);
diag[8] = static_cast<int32_t>(session.channelGroupIdx);
```

TMR eager 诊断任务 `task_20261019_220656_145189114696` 的一次失败记录：

- 48 个 `event.valid()` 均为 1，48 个 `session.valid` 均为 1。
- worker **0, 1, 2, 17, 20, 30, 34, 35, 37, 46, 47** 的 `Wait()` 返回 0；对应 11 行各 1024 个 FP32 保持输出初始化值，其余行正确；24 条 AIC 输出全部正确。
- `session.channelGroupIdx` 实测为：
  `[2,2,5,5,8,8,11,11,14,14,17,17,20,20,23,23,1,1,4,4,7,7,10,10,13,13,16,16,19,19,22,22,0,0,3,3,6,6,9,9,12,12,15,15,18,18,21,21]`。
- 原生 CCE `get_block_idx()` 与上述数组相同；原生 `get_subblockid()` 在这些 user kernel 上均为 0，而 Simpler 传入的逻辑 block/subblock 正确区分了 48 个 worker。另有逐 worker 唯一标记确认诊断代码确实执行，不是读取未写入的 0。
- 失败不依赖 graph capture：纯 eager 重复调用也出现。

### 源码对应与建议

当前 PTO-ISA `include/pto/comm/async/sdma/sdma_async_intrin.hpp` 的 `BuildSdmaSession` 在自动选择通道时使用原生 `get_block_idx()`。在上述 Simpler MIX 启动方式下，两条 AIV 选择同一 channel group。通道有共享 SQ head/tail、完成状态等，不能把 48 个并发发起者视为 48 个独立队列。这是已确认的通道别名；它与 Wait 失败的完整因果关系仍需显式唯一通道对照进一步验证。

建议 runtime 提供**按物理 AIV 唯一、稳定**的 SDMA channel ID，由 PyPTO/PTOAS 显式传给 context/session。PTO-ISA 已有显式 `channelGroupIdx` 的 session 构建入口。不要直接用逻辑 task ID 替代物理 ID，否则多个 task 同时运行仍可能碰撞；也不能直接使用此次读到的原生 subblock ID。

建议补上完整 MIX 双 AIV、重复 eager、首次 capture/replay 和多 task 并发的测试，断言有效 event/session 且 Wait 成功，而不仅验证拷贝结果（空事件的 Wait 可能直接返回 true）。

补充：当前用例的每 worker GM subview 使用本地 #3042 原型，仅构造指针偏移，不做数据拷贝；会进一步简化成不依赖该原型的复现。另一个诊断中 `pl.cast(wait_result, pl.INT32)` 被降为 `arith.extsi i1 to i32`，true 变成 -1，已从本条 SDMA 证据中排除，不能把该诊断误判成单发起者 SDMA 失败。
