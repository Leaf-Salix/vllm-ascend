## 得到的结论

两任务小图可以接到首次探测时尚未出现的后继，并经原执行器形成同核交接。
独立计算标记确认，最新候选的两轮AIC测试分别有6条和4条交接在后继Scalar前缀结束后，
原Cube计算仍未完成；后一次图重放检查还观察到1条。不能把所有后到交接都算成计算收益。

输出、真实fanin读取、保护区和最新候选的图重放结果通过。当前候选在两任务小图里，
AIC mean减少1.57μs，AIV增加6.49μs，尚无普遍性能收益，不据此替换CSA收尾。
本轮没有新的CSA、Native或16卡性能结果；CSA仍以过程054的无插桩结果为准。

## 小图及控制变量

每图两个独立编译的SPMD任务，24个AIC或48个AIV block。生产者写结果，后继有真实
数据依赖：只在局部Wait后读取前驱结果，并核对读取值。两边均显式保留原本的
allow_early_resolve=True，运行时仍验证pending资格、本核流水及完整fanin。

`once`保持原执行器单次交接探测；`late`在局部Set适配器中增加等待期间的后继检查。
后继已出现则直接返回，未出现时才发出完成通知，并轮询既有DATA_MAIN_BASE与GM完成标志。
返回后仍由原执行器决定是否交接，没有在适配器内发FIN/ACK、修改队列或替换核分配。

**观测边界：**测试的首次时间点位于局部Set中，比原执行器的返回后探测略早。
因此“Set首次未见、之后见到”不能逐条等同于“原执行器必然漏掉的机会”。
两条路径的完成时间会反过来影响原调度器的正常选择，也不能把两次交接数直接相减
当作固定任务集合上的净新增数。需要把接续检查放到正式运行时位置才能精确核实这一项。

## 为什么增加独立计算标记

阶段01采用RuntimeBarrierAll，余下等待包含了新增加的MTE3通知，不能证明原M/V仍在计算。
后续在原计算流水末尾加独立M→S或V→S标记，使用现有AicAllPipes/AivAllPipes诊断协议。
AIC把额外MTE3通知接入FIX再等待FIX→S，保证通知本身也在真实FIN前完成；AIV直接等待MTE3→S。
因此既能读取原M/V等待结束点，又不会漏掉新增搬运的收尾。

判据为：同一物理核及匹配的派发序号；后继前缀结束不晚于运行时开始等原计算；
独立M/V实际等待大于5个原始tick；后继数据操作不早于前驱完整完成。
这是充分的重叠证据，不是必要条件：计算若在前缀期间完成，不能只靠Wait处零等待断言没有收益。
本用例的长Scalar循环是人为诊断负载，不能据此把真实CSA任务定性为Scalar bound。

## 最新候选如何减少入口工作

通知在+1与−1间交替，源是设备上已经初始化的两个不可变cache line。只有未见后继时，
才失效并读取上一次通知，选择相反的值发出DMA；整个任务入口不再清零目标、重写源及写回两行。
前次通知在真实FIN/后继Wait之前完成，后一次才允许复用；当前还不是通用运行时workspace接口。

将搬运设置和轮询移入noinline设备辅助函数，使其局部变量不必贯穿原计算及已有后继的路径。
这些是已实施的代码变化，尚未用同条件前后测量量化各项独立收益。

## 接入CSA之前仍需完成

1. 正式预留64B本地scratch。当前小例子仅使用L1/UB末尾确认未占用的64B，不能复制常量到任意CSA任务。
   PyPTO已有reserve_buffer和内存分配器，需把内部协议预留纳入它们，并检查全部MIX成员。
2. 正式预留通知使用的同步事件。当前小例子原计算只占用event0/1；通知使用event7。
   PTOAS现有异步尾部event7预留不覆盖本候选所有MTE3汇合边，需要扩充资源合同及冲突检查。
3. 提供生命周期正确的每物理核GM通知区，避免测试trace成为算子入参要求，也不能改变依赖图。
4. 保留现有立即交接路径，在原探测位置核实后到窗口，避免把更早的Set时间点混同于原运行时探测。
5. 以上具备后，先做128K/B16同SDK、无诊断的CSA对照，并检查输出/状态，再决定默认策略。
   显式局部Wait与chip swimlane/PMU/参数dump的串行回退继续保留，不做自动前缀识别。
