# 历史初版：只有Cube与部分带宽，不能当完整CSA roofline

本文件保留首次评估及遗漏Vector后的修正过程。最新完整资源模型见
[FULL_ROOFLINE.md](FULL_ROOFLINE.md)，本历史稿中的“尚缺Vector”等状态已被后续工作替代。

日期：2026-10-20。先完成相邻 `static_history_audit` 的新旧静态性能核对，
再开展本评估。本目录只有离线模型，没有新增 CSA 性能测试或优化候选。

更正：初版只完成Cube与主数据带宽模型，遗漏了Vector下界，因而不能据此
判断整层距离硬件极限多远或定量计算剩余优化空间。
当前矩阵分块在理想 Cube 吞吐下约需162、287 μs；
主数据冷缓存的一次读取约需165～197、204～262 μs。相比802、1168 μs实测，
只能确认与这两项局部下界有明显差距。Score生产消费链及Attention
数据交接/Vector链仍值得诊断，但不能直接把该差距计为可实现收益。

这些数字是乐观资源模型，**不是保证可达的完整 CSA 耗时**。Vector 特殊指令、
Scalar 寻址、片上端口、同步及串行依赖不能由一个 FLOP 数替代。

## 1. 范围与硬件口径

采用最新七档中已实测的动态源码13259f92，以及同次结果中的形状、NZ格式和
策略；37个正式源码文件与该测量快照逐字一致。范围为：

`HC_pre → 输入RMSNorm → Q/KV/两套压缩/Indexer/稀疏Attention/O投影 → HCpost`

TP1，正式 `/data/model/DeepSeek-V4-Flash-0731-w8a8` 第4层，S6，64个
Attention heads，head_dim512；Indexer为64 heads、dim128。没有MoE、
整模型、网络通信或DP16成本。模型称W8A8，不意味着所有矩阵都用INT8：
Q_A、KV、两套压缩及O_A实际仍为BF16。

本机 `aclrtGetSocName()` 返回 `Ascend910_9392`。CANN platform配置为：

| 资源 | 本评估采用值 | 依据 |
| --- | ---: | --- |
| 单个逻辑 device | 一个 die | 本机每device 64GiB，任务72个核角色 |
| 可用 AIC / AIV | 24 / 48 | `Ascend910_9392.ini` |
| Cube 频率 | 1.85 GHz | platform配置；同日原始Profiler也记录1850 MHz |
| BF16/FP16 Cube峰值 | 363.7248 TOP/s | `24×1.85e9×2×16×16×16` |
| INT8 Cube峰值 | 727.4496 TOP/s | `24×1.85e9×2×16×32×16` |
| HBM峰值带宽 | 1.6 TB/s | 每die规格上限，未声称是本机可持续实测 |
| L2容量 | 192 MiB | platform配置201326592 bytes |

一次乘加计两次运算，INT8 的单位为整数TOP/s，不能混称BF16 TFLOP/s。
两个精度共享Cube资源，计算其等效占用时必须相加：

```text
t_cube = OPS_int8 / P_int8 + OPS_bf16_fp16 / P_bf16_fp16 + OPS_hc_fp32 / P_hc_fp32
t_hbm = HBM_bytes / bandwidth
t_resource_floor = max(t_cube, t_hbm)
```

上式最后一项假定跨阶段的计算和访存能理想重叠，因此只是资源下界。
不能把它当作遵守全部真实依赖后一定能达到的执行时间。

厂商论文明确说明910C双die、每die24 AIC/48 AIV、64GB及1.6TB/s。
整张双die卡的3.2TB/s不能用于本次单device测试：
[Huawei CloudMatrix384，§3.3.1](https://arxiv.org/html/2506.12708v2#S3.SS3.SSS1)。
Cube的每周期算术模型参考
[Communications of Huawei Research，Cube/Vector资源讨论](https://www-file.huawei.com/admin/asset/v1/pro/view/6ca306adab0a4852bacffce25f5573ec.pdf)，
并按本机频率换算。

HC投影的FP32吞吐暂按BF16的1/4建模，属于明确假设。改成1/1～1/8时，
B16总Cube下界为160.94～162.87 μs，B28为285.55～289.10 μs，不影响主要结论。
没有把模型里这段FP32算术偷偷改成BF16。

## 2. 数学工作量不能按普通128K dense attention计算

设 `T=B×S`，本轮S6，历史H。压缩比4，Indexer扫描约 `L=(H+S)//4`
个候选。128K场景为32769个压缩位置；每个query实际可见数仍取
`(position+1)//4`，前后query相差一个位置。

真正的Attention只处理滑窗128＋压缩Top512，共640候选，不扫描整段128K
的BF16 KV。当前测试五个K128块均有效。

主要矩阵数学如下，乘加按2计：

| 阶段 | 有用运算量 |
| --- | --- |
| HC投影 | `2×T×16384×24`，FP32 |
| Q_A / KV | `2×T×4096×1024` / `2×T×4096×512`，BF16 |
| 主压缩 value+gate | `4×T×4096×1024`，BF16 |
| Indexer压缩 value+gate | `4×T×4096×256`，BF16 |
| Q_B / Indexer query投影 | `2×T×1024×32768` / `2×T×1024×8192`，INT8 |
| Indexer query Hadamard | `2×T×64×128×128`，BF16 |
| Indexer QK | `2×64×128×Σ每query可见候选数`，INT8 |
| Indexer head加权归约 | `2×64×Σ每query可见候选数`，FP16 |
| 稀疏 Attention QK+PV | `4×T×64×640×512`，BF16 |
| O_A / O_B | `2×T×8×4096×1024`，BF16 / `2×T×8192×4096`，INT8 |

脚本还计入Indexer head weights投影、compact Hadamard等小矩阵。
普通Vector归一化、RoPE、量化、排序和HCpost未伪装成Cube矩阵工作。

“有用数学”与“当前执行的矩阵量”有以下区别：

1. 矩阵M轴按硬件16行分形对齐；B28的T168对应176行的部分矩阵计算。
2. 小中O_B仍按M32/M96执行，例如B8/T48的O_B计算96行；大M128路径已
   删除多余尾行，不能继续按256行给B28计账。
3. 长历史Score仍整块处理1024列，32769位置需要33块；尾块的无效候选
   不产生有效Top-K，但占用矩阵计算。
4. Score的head加权归约使用`M16×K(G×64)`的系数矩阵。其有效块呈对角，
   但Cube仍计算零系数及填充输出行；不能只按每query64项求和计算其成本。

第4项使当前WS矩阵量约为有用归约的16倍，再叠加历史尾块。
B16有用归约约0.403G、实际约6.644G，理想Cube时间约18.27 μs；
B28约0.705G→11.627G，约31.97 μs。这是可审视的数学映射成本，
**不等于改到Vector就必然更快**：Vector吞吐、64项归约及精度边界还需评估，
改变数学表达或舍入采用前仍须另行确认。

## 3. 七档理论账本

单位均为μs。HBM列为“主矩阵权重首次读入、Indexer key/scale首次读入、
hidden输入输出”的冷缓存模型：

- 左端：同请求S条query最大程度复用选中KV；
- 右端：每query的640条KV读取均需要从HBM供给；
- 两端均未将所有中间GM buffer强行算为HBM读写，也未计state/页界等小项，
  因而仍偏乐观。它不是热重放时实际HBM耗时的置信区间。

| 场景 | 有用数学Cube下界 | 当前分块Cube下界 | 冷缓存主数据HBM模型 | 当前动态完整L1 |
| --- | ---: | ---: | ---: | ---: |
| 128K/B4 | 35.53 | 44.42 | 124.72～132.90 | 476.40 |
| 128K/B8 | 71.06 | 85.31 | 138.00～154.36 | 626.50 |
| 128K/B16 | 142.12 | 161.77 | 164.57～197.29 | 802.20 |
| 128K/B24 | 213.18 | 242.65 | 191.14～240.21 | 1039.82 |
| 128K/B28 | 248.70 | 287.07 | 204.42～261.68 | 1167.72 |
| 8K/B16 | 74.66 | 76.66 | 124.63～157.35 | 644.08 |
| 8K/B32 | 149.32 | 153.33 | 137.83～203.27 | 933.58 |

据此取`max`，理想资源下界在B16约165～197 μs，B28约287 μs。
这不是“CSA应该跑到165/287”的承诺，尚未加入后面描述的Vector、
片上中转和真实依赖成本。热缓存下HBM项会不同，不能声称上述冷缓存下界
就是当前ACLGraph重放的精确下界。

作为敏感性对照，若人为只给50%的Cube峰值和60%的HBM峰值，
相同资源公式在B16得到约324～329 μs，B28约574 μs。
这些效率系数并未实测，仅说明“低于峰值很多”的资源预算仍低于当前耗时，
不据此宣称实现后的收益或可达时间。

## 4. 带宽必须分HBM、GM请求与片上中转

### 4.1 必须保留的模型数据

主要矩阵权重合计178.29 MB（170.03 MiB），其中：

| 权重 | 数据量 MB |
| --- | ---: |
| O_A，BF16 | 67.11 |
| Q_B，INT8 | 33.55 |
| O_B，INT8 | 33.55 |
| 主压缩两矩阵，BF16 | 16.78 |
| Q_A，BF16 | 8.39 |
| Indexer query，INT8 | 8.39 |
| 其它主矩阵合计 | 10.52 |

权重只能作为同一模型常量复用，不能从当前工作区容量推算“每轮必读的字节”。
Indexer的key+scale按每候选128B INT8＋2B FP16计算，B16约68.16 MB，
B28约119.28 MB；同一请求G6的六条query可共享key读取。
稀疏Attention一次query需要640×512×2=655360B；跨query是否命中相同Top-K、
以及是否仍在L2，决定HBM供给量。

当前L2为192 MiB。仅权重已约170 MiB，再加长历史key和Attention数据，
不能假定整层工作集全部常驻。另一方面，不能反过来把所有GM访问都算为HBM：
环槽、局部结果和重复权重可能命中L2。

核对还确认既有缓存提示限制仍在：PyPTO IR有`l2_bypass`属性，但这份PTOAS
没有offset时生成普通TLOAD；最新实际C++也没有TLoadL2Hint。
因此此模型没有将源码BYPASS声明误当成“每次权重访问必然绕过L2”。
这是历史日志已记录的能力边界，本轮没有修改组件或重复提出新问题。

### 4.2 Attention的主要GM访问

每个K128块中，KV由AIV采集后写GM环槽，AIC读入一次L1，同时供QK和PV；
QK score、softmax probability、PV还分别跨AIC/AIV交接。

| 数据流 | 128K/B16，MB | 128K/B28，MB |
| --- | ---: | ---: |
| Native KV→AIV | 62.91 | 110.10 |
| AIV写KV环槽 | 62.91 | 110.10 |
| AIC读KV环槽 | 62.91 | 110.10 |
| QK score写＋读 | 31.46 | 55.05 |
| probability写＋读 | 15.73 | 27.53 |
| PV写＋读 | 125.83 | 220.20 |
| query读＋packed输出写 | 12.58 | 22.02 |
| **合计** | **374.34** | **655.10** |

这是已明确的大项GM请求量，不含某些小统计量、metadata和信号。
它同时是当前有价值的中转优化方向，不能直接除以HBM峰值称为真实访存耗时。

若这些GM请求的有效聚合服务率分别为2/4/6 TB/s，单独服务它们需：

| 场景 | 2 TB/s | 4 TB/s | 6 TB/s |
| --- | ---: | ---: | ---: |
| B16 | 187.17 | 93.59 | 62.39 |
| B28 | 327.55 | 163.77 | 109.18 |

这些是带宽敏感性参数，**不是宣称本机L2实际提供了某个聚合带宽**。
MTE端口、读写方向及小DMA效率会进一步约束结果。
由此可见，只给Attention的22/39 μs矩阵下界会严重低估它的数据供给成本。

## 5. 与现有真机关键路径证据结合

使用13259f92正式源的既有72核阶段时戳，没有新增插桩测试。
表中“阶段区间”取每核阶段扣除外层GM依赖等待后的中位数；
仍包含内部READY/ACK、搬运、Vector/Scalar及探针，不能当作纯引擎运行时间。
这些阶段有重叠，不能把中位数相加复原完整L1。

| 阶段 | B16矩阵下界 | B16阶段区间 | B28矩阵下界 | B28阶段区间 |
| --- | ---: | ---: | ---: | ---: |
| Indexer Score，按最忙核计算 | 91.33 | 192.64 | 170.21 | 329.82 |
| Attention QK+PV，全24核资源模型 | 22.14 | 153.47 | 38.75 | 304.19 |
| Q_B，全24核资源模型 | 8.86 | 60.57 | 16.24 | 88.91 |

Q_B实际分给20个AIC，因此其理想值还应按20核和列块尾波修正；表中采用全24核
只是资源模型，不能据此说20核实现本应达到8.86 μs。
O_A也有分组就绪及列块尾波，不将全核峰值直接当作阶段可达值。

Score的24核块数由脚本按源码重新计算，并与已有真机探针逐核一致：

- B16每核22个score块，已经均衡。仅换核编号不能消掉这段算术。
- B28每核33～41个，平均38.5。理想全均衡的矩阵时间159.83 μs，
  当前最忙核170.21 μs；仅消除此分配差，峰值模型只差10.38 μs。
  故不能指望调整几条核的工作量解决整层271.64 μs的剩余目标差距。

B16/B28 Score现有AIC等待ACK中位14.65/31.77 μs，AIV等待READY中位
57.27/113.09 μs。它支持先检查Cube生产链，但也说明加快Cube后可能转为
Vector排序/归约受限；不能将Cube算术下界独立当成整个Score可达耗时。

## 6. 还剩多少空间，优先看什么

当前分块的等效Cube理想占用仅为完整L1的约20.2%（B16）和24.6%（B28）。
这不是PMU测得的利用率，也不是说剩余时间都是浪费；其中包括必需的
非Cube计算、数据转换和依赖。不过可以明确：当前完整CSA不是已经逼近
Cube算力上限后只剩几微秒可挖。

对原多task完整L1降低30%的目标，在本轮配对基线下为：

| 场景 | 多task L1 | 30%目标 | 当前动态 | 还需净省 |
| --- | ---: | ---: | ---: | ---: |
| 128K/B16 | 873.16 | 611.21 | 802.20 | 190.99 |
| 128K/B28 | 1280.12 | 896.08 | 1167.72 | 271.64 |

这些目标并未被资源下界否定，但仍需要改变主要阶段的效率或重叠，不能靠
把理论差额当收益来宣布可达。下一轮若恢复优化，优先顺序建议为：

1. **Score整段流水**：在已有QK/FIX/WS数据流上看实际持续吞吐，
   同时约束MTE1、FIX和AIV消费。B16/B28矩阵下界与阶段区间各约差101/160 μs，
   这是诊断空间，不能全部计作预期收益。仅挪核或删少量Scalar不足以填平。
2. **Attention数据交接与Vector链**：优先减少重复GM中转、降低小DMA和
   在线归并开销、提高三槽覆盖。其矩阵算术很小，单纯提高QK/PV的Cube
   峰值利用率无法解释或解决大部分153/304 μs区间。
3. **投影的有效权重复用和跨分支重叠**：权重大而M小，先核实真正的缓存
   路径和请求次数。源码prefetch/BYPASS存在不代表硬件生效；若数据命中L2，
   再往HBM预取可能没有收益。不能只按矩阵FLOP决定下一步。
4. **WS数学映射作为需另议的方向**：16行输出和对角系数带来的额外运算
   已定量，若要改数学映射，需要同时估算Vector资源和确认数值边界，
   不在本轮擅自采用。

当前只是评估，不启动以上候选；此前“本轮优化结束后停止”的约束保持。

## 7. 补充：遗漏Vector后的结论修正

用户指出只有Cube下界，没有Vector。这是初版分析未完成，不能以
“Vector不是普通FLOP”作为省略理由。官方有A2/A3的
[Vector指令理论性能表](https://asc.gitcode.com/api/appendix/vector_instruction_theoretical_perf_summary.html)，
需要按实际指令类别、重复次数和核分工计算，而非套统一TFLOPS。

相关A3吞吐为：FP32 Add/Mul每周期64元素，Exp/Div为32元素，
Sort32/MrgSort为2个排序项。排序项是(score,index)队列条目；
PTO暂存的1024个FP32位置只对应512个排序项，不能重复计算。
归约、广播、类型转换和Gather还须按实际ISA展开，不能直接按Python
helper的名字或调用次数折算。该资料是asc-devkit master预览，应保留版本边界。

先对当前长G6路径完整计算了排序这一子集：每叶512/1024/2048分段的Sort32、
各级MrgSort、叶内根累积，以及最终query根归并，映射到真实48个AIV。
按1.85GHz及官方吞吐得到以下峰值服务时间模型：

| 场景 | 排序/归并最忙AIV，μs | 对应Score最忙AIC矩阵下界，μs |
| --- | ---: | ---: |
| 128K/B4 | 21.86～22.56 | 24.91 |
| 128K/B8 | 40.13～40.82 | 45.66 |
| 128K/B16 | 80.26～81.64 | 91.33 |
| 128K/B24 | 118.73～119.97 | 136.99 |
| 128K/B28 | 148.20～149.86 | 170.21 |

范围来自最终多路MrgSort在任一输入耗尽时提前结束；使用最少/至多处理量，
不是测量波动区间。该模型忽略指令头开销、UB重排、其它Vector算术、DMA、
Scalar和同步；没有使用改变退避的模拟流水推导真机等待时间。

**仅排序就已经与Score的Cube矩阵时间接近，不能将Vector当成免费。**
上表仍不是完整Vector下界：尚缺softmax/在线归并、各归一化/量化/RoPE、
压缩pool、HC门控/Sinkhorn/HCpost及其实际展开/分工。8K是另一套G2半叶
排序分支，此处没有借长G6公式填数。数据见`VECTOR_SORT_BOUND.json`，
脚本为`vector_sort_bound.py`，不启动设备。

现有13259f92真机阶段探针中，Score Vector的B16/B28区间中位为181.67/
324.70 μs，Attention Vector为158.41/304.77 μs；这些仍包含内部等待、
搬运、Scalar和探针，**不能用作纯Vector理论下界，也不能与Cube区间相加**。
旧独立Score PMU的aiv_vec_time约99.17 μs属于10/18另一构建和场景，
同样不能直接代替当前完整CSA的Vector下界。

完整模型至少需同时考虑：

```text
T >= max(Cube资源下界, Vector资源下界, HBM下界,
         L2/片上端口下界, 实际依赖链下界)
```

每核指令工作量按其类别吞吐计算后，还需保留最忙核与指令依赖限制。
Cube和Vector可重叠，所以也不能简单将两项整层峰值服务时间相加。
初版165～197/287 μs只能继续标为Cube+HBM的局部资源下界；
完整Vector与依赖链模型补齐前，整层剩余空间的定量结论保持未完成。
