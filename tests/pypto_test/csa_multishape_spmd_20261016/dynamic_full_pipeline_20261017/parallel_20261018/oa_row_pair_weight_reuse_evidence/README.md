# O_A 两个 M 行块共享权重：HC_pre 思路的动态区间迁移

用户再次要求参考 hc_pre 与静态 SPMD。当前候选直接修改正式动态源码；
旧静态保持只读，不使用冻结 shape 生成器，不替换当前已采用策略。

## 新方案与既有尝试的区别

hc_pre.py 的大档用 M48/M64 减少重复读权重。本方案不是复制其 T96 特化：
CSA 原 O_A 的 128<T<=256 区间是两份 M128×四个 N256。改为八个 N128，
每个 N 同时计算前128行和实际尾行，共享全部 K4096 权重。两个独立 Acc
各物理128×128 FP32；v1保留原 N256 路径的 L0 K64 顺序，v4改为K128。

旧 oa_pair_manual 是相邻 **N** 输出共享 **A**；这里是两个 **M** 行块共享
**B**。旧 QB resident 属于另一 INT8 投影，也不是本次 BF16 O_A 候选。
跨独立行换计算先后不等于硬件逐bit已证明，必须由正式权重完整对照检查。

权重逻辑请求128→64MiB，输入额外 T×256KiB：T144/168/192时净减少
28/22/16MiB；T256时合计字节不减。这里只是请求量推导，不是 HBM 或收益。
分界依据是两份 M128 容量和复用成本，不按七个回归点建白名单。

另一个结构收益来自分工：原每组8任务前4个满M128，后4个尾M(T-128)，
24条带使满块/尾块落在固定的不同核上；新8任务均含两个半列宽M块。原最忙
核每K的输出元素数为3×128×256，新为3×T×128，T144/168/192分别为原来
的56.25%/65.625%/75%。这些不是时间降低比例：搬运、指令数量、原尾核能
否提前做后续任务及跨组通知均会影响实际完整L1，不能据此预记性能改善。

## 同步及动态合同

每组任务数均8，全局 owner=(group×8+column_task)%24。量化原本等本组
所有列/行生产者；新的同一八个 owner 全部发布后，两行块所有列均已完成。
组通知、FFTS、quant/OB及其它数学不变。T、有效尾行、页表和Q/L仍动态。
binding 拒绝把开启策略用于区间外，默认开关 False，不默默套用非法分工。

嵌套stage2是待审计的实现选择，不能只看源码便声称真实双缓冲成立。
完整符号编译须检查两Acc/Left/Right/L1地址、别名、事件及动态尾行。

首次 CPU 命令误指不存在的复现脚本，未进入编译；保留 cpu_long_v1.log。
本目录新增明确 run_cpu.sh 后继续，不将这个命令错误上报为组件 bug。
所有 CPU/设备结果在终态后追加；当前没有性能结论。

  cpu_long_v3报Left262144B>65536B，属于该自动流水表达资源过量，未上卡。

  但lowering引入Mat→Mat TMOV，PTOAS正确拒绝。最小CPU复现也同样失败；

  说明与同窗口phi问题#3016的区别，附完整复现和buffer轮转建议。未改共享库，
  未宣称干净main已完成同一复现，不删拷贝来冒险越过正确性边界。
- source_candidate_v4只在外层使用普通range，K128显式交错保留。
  cpu_long_v5完整通过：两Left与两Right各32KiB，两个Acc各64KiB；
  无Mat→Mat copy。该版不声称外层有两槽L1预取。后续设备结果见下节。

K128改变硬件分块，必须重新通过原精度检查，不能仅据FP32代数等价预记PASS。
后续同轮性能分母仍是原多task完整L1；未新增Native或静态测试。

然后只恢复本轮自有改动到f222a917；未改其它会话文件。完整候选留在
`source_candidate_v1..v4`。恢复记录为 `FORMAL_RESTORE.json`。
额外CPU关闭分支核对：130根/58动态轴/一个MIX，移除整行注释后C++与
同编译器旧关闭路径完全一致；没有借关闭开关偷偷改变其它数学。
该核对是生成物证据，不替代设备正确性或性能。
