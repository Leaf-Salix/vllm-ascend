# QR+B 常驻基础上的双 N128：只读定界

2026-10-18。**结论：资源和数学上可表达，但本轮停在设计，不追加 CPU/NPU。** 当前 QR+B 两个代表已经完整精度通过却没有完整 L1 收益，旧 `qproj_l1_columns` 的双 N128 也只得到噪声范围内的差异。现有证据不足以支持继续尝试这一局部流水分块；不能因为预算容纳两槽就继续扫参数。

本报告仅阅读正式/冻结源码、已有生成物和历史记录；没有修改候选、正式源码、依赖或生成产物，没有编译、设备任务和 hash。

收到这些结果前，只能给双N128保留“若现有QR+B基线有效，再考虑一次CPU”的条件判断；条件现已不成立，不能把该早期意见保留为继续编译授权。

## 现有串行边与双槽最多改变什么

现有冻结源/生成物在：

```text
C=/data/pyptouser/qinchuanyu/pto-eager/vllm-ascend-dsv4-pto-0251rc1
E=/data/pyptouser/qinchuanyu/pto-eager/.worktrees/csa-ultra-sync-20261018/tests/pypto_test/ultra_qb_qr_b_resident_cpu_20261018
PTO=$E/cpu_v1/kernel/ptoas/dynamic_csa_full.pto
CPP=$E/cpu_v1/kernel/kernels/aic/cube_schedule.cpp
```

PTO `:1476–1520` 的QR/B Mat分别262144 B，合512 KiB；Left `[128,256] INT8`为32 KiB，Right `[256,256] INT8`为64 KiB，Acc `[128,256] INT32`为128 KiB。Right没有下一槽。

C++ `:10466` 等 M→MTE1，`:10469`提取下一Left，`:10479`提取下一Right，`:10482`MMA，`:10483`归还槽；`:10453`的FIX→M保护前一M的Acc写回。因同一Right覆盖，下一K完整64 KiB权重搬运必须等上一K MMA使用完。此为实际依赖链，不代表已测出这条边的耗时或其占整层比例。

设同一原N256 owner内两条链为N0/N1。双Right能尝试把边拆成：`MMA(N0,k)→Right(N0,k+1)`，让这32 KiB搬运与`MMA(N1,k)`重叠；无需等同K两条链全结束才准备N0下一K。这只能提前部分供数，**不能删除所有K间等待**：单份共享Left仍供同K两个MMA使用，下一K Left要等两者都读完；另一个Right槽也要等自己的消费者。

例如固定四个数学K块可在`MMA(N0,k)`后先产生`Right(N0,k+1)`、再提交`MMA(N1,k)`，使未来N0与当前N1两份Right同时存活。实际编译器还必须把N1当前块就绪事件放在未来N0搬运之前，否则N1又等未来供数，预期窗口消失。不能只由源码次序或两个地址宣称硬件重叠。

## 成立所需的资源与新增代价

保持外层N256 owner、两个动态M128、QR/B满512 KiB Mat不变；只在每个N256内部使用两个N128 Acc。不要把全局`QPROJ_MM_N_TILE`改成128，否则会改变列任务数和owner。各半块分别写原 `[col:col+128]`、`[col+128:col+256]`，发布仍在原owner全部工作之后；原QB等待公式不变。

| 对象/每个M、原N256列组 | 当前N256 | 设想双N128 |
| --- | ---: | ---: |
| Right容量 | 1×64 KiB | 2×32 KiB |
| Acc容量 | 1×128 KiB | 2×64 KiB |
| 共享Left | 32 KiB | 32 KiB，两个N消费同一K片 |
| Left extract | 4 | 4 |
| Right extract | 4 | 8 |
| MMA | 4 | 8 |
| FIX store | 1 | 2 |

MMA、Right指令和FIX调用数翻倍，但有效运算量、Right总字节、输出字节及GM QR/B字节不变。每核5或6个N256、每N两个M时，MMA从40/48次变80/96次，store从10/12次变20/24次；Scalar还需维护两Acc、两份列偏移、更多tile与事件。两个Acc同样占满128 KiB，不增加下一M的Acc重叠空间。

“共享Left”这里只按**单物理槽**计算。旧实验为了预取下一K另有第二Left；若照抄其下一Left提前产生顺序，本版Left将变成2×32 KiB=64 KiB，须明确这是另一项资源/依赖变化，不能暗中把它算成单Right因素对照。单Left不预取下一K的边界已经足够说明可提前的主要是半份Right。

各Acc必须独立初始化K0，再按K256/512/768累加INT32；T129/255/256两M有效行仍为128+1/127/128。两条N链没有相互归约，不改变任何head512的后续RMS顺序。容量可容纳不替代动态compact/地址生成验证。若以后有新证据重新立项，必须查实际两个Right地址0/32768、两个Acc地址0/65536、无额外Mat，并验证上述分离事件；本轮不为取得这些图样而编译。

## 历史排重：这是旧手段在新基线上的对照

`C/tests/pypto_test/csa_multishape_spmd_20261016/QPROJ_L1_COLUMNS_EXPERIMENT.md`、`qproj_l1_columns.py:body`、`qproj_l1_columns_codegen_audit.json` 已记录完整同类思路：固定T96、20个worker，原N256 owner内拆两个N128，各自四K256，QR入口一次、两份K1024×N128权重驻L1；真实Right0/32768、Acc0/49152，Left0/24576两槽。不是“从未尝试过的双N128”。

其同进程三窗为现选805.28/808.92/810.24，双列806.02/804.06/810.32 μs；中位808.92→806.02（0.36%），范围明显重叠，未采用、不扩测。不能把首次不同作业806.46与另一运行时间拼成新收益，也不能把该弱结果说成已证明双槽一定更慢。

本次设想只有这些区分：当前为24核、动态T129..256的两个M128，QR/B各256 KiB已经存在于被测基线；拟在这个基线上单独拆N，因而可以隔离L0分块，而旧实验同时引入了常驻和双列。但这只改善实验的解释性，**不是新的正向性能依据**。当前父候选也无收益，不能用“动态/大T不同”绕过旧负面或弱证据继续测。

`parallel_20261018/oa_pair_explicit_mat_cpu_evidence/README.md` 的OA最小probe证明手工生存期可以得到Right两槽、Acc两槽；v1因Mat回边拷贝失败，v2固定四数学K256后CPU通过。它是BF16/K4096、内部K128、独立最小probe，只证明某种表达能力，既不证明本INT8/K1024版本生成相同，也没有设备性能证明。若未来重新立项，应保留外层动态N/M，只把四数学K块有限展开，不重做导致Right提前活跃的pipeline或Mat回边；本轮不写候选、不申请新测试。
