## 锚点决定了这些数值能说明什么

- `body_total` 已排除前置输入 acquire，仍含叶准备、全部step、leaf排空和末端局部等待；`step_total` 含步复用ACK、全部16面板及READY发射。ACK还含**step外**的leaf尾排空，所以不能从step直接扣ACK得到纯算术。
- `page_key_sample` 是j8所在位置的下一面板Key预取：页表/guard、TLOAD、原local wait及L1→L0发射都在里面。3.83–3.87μs是每核22次样本的累计中位，不是整段Key加载成本，也不是GM带宽。
- `qk_fix_sample` 分成QK发射和FIX两个小岛，中间保留原WS。22次总计只有0.18–0.20μs，恰好提醒这是Scalar发射/原等待的观察，**不能据此说QK/FIX执行几乎免费**。
- `ws_sample` 合并三段：上一面板FP16从Mat提取到Right、WS发射、输出设置/原M→FIX等待及TSTORE。它不是一个独立WS引擎时间，包含对前一QK/FIX和L0/FIX复用的等待；7.43–7.50μs不能成为把WS搬到AIV的依据。
- `local_wait_sample` 是上述page/QKFIX/WS内部10个站点的嵌套总和。保留原样报告，不相加，也不从父区间相减。异步流水会把某类数学的压力体现在后面的等待点，源码类别不能直接映射为硬件成本类别。

所有当前函数内锚点取自**此次真实任务**的codegen_audits，已随JSON保存；不是拿设计时旧行号代替本次代码。完整机器码指令排序/spill仍没有可读反汇编证据，本轮不重新审查编译器。

## 当前支持的下一步与边界

唯一有新增事实支持的分析重点，是**同组AIC/双AIV的消费相位和ACK背压**：约30μs的ACK累计及0..7/8..23组别差异，值得与已经保存的端点对齐。它不等于30μs可省，更不支持删ACK、无依据增大FIFO或重分物理核。

本记录仍将step复用ACK与leaf排空ACK合并，也将WS的三段合并；固定j8不代表首尾/其他面板。因此不能从当前数据把约233μs的服务区间落实为一份可以删除的大额重复work。已审计的WS→AIV会增加32倍交接并改变数值归约问题，当前样本没有推翻这些反证。没有提出新的实现/上卡候选，也没有把样本乘16、跨轮相减或将插桩时间算成性能收益。
