# O_B→八组反量化→HCpost：逐组消费只读审计

2026-10-18。**数学和数据依赖允许逐组消费，但本轮建议暂不制作实现/设备候选。**
最小行外层方案只可能隐藏每名 AIV 第一行的部分归约，额外通知/获取明显增加；
组外层可覆盖更多行，但要增加长期存活的多行 UB 累加器，或承担可量化的 GM
往返。已有时钟只量到整个 O_B 和最终输出，尚未把潜在重叠窗口与这些成本分开。
这不是“已经证明没有收益”，也不是数学阻塞；只是当前不足以支持优先实现。

唯一对象是正式动态完整 CSA 中这一段。本文没有更改正式源码、数学、phase、
阈值、工作区或依赖，没有新编译、设备任务和性能测量。分析脚本只读现有文件。

  本文不能把同一项再当新优化。
- 历史 `query_group_schedule_model.py` 按 **query/token 行** 拆分整条链，
  不是保持每 token 八组归约顺序的 O_B partial 提前消费。
- 旧 HCpost 已按整行 4096 列计算，O 投影 BF16 tile 直接传 HCpost，**不存在
  可再消除的 out_bf16 GM 往返**。旧读点审计已记录每行 8 个 scale 与 20 个 gate

- 在所查记录中未找到“每组 O_B 发布→AIV 按 g=0..7 提前反量化”的相同实现或

## 正式现状：谁写、谁读、何时通知

阅读顺序及精确函数范围见 `evidence.json.source_locations`：

1. `cube_schedule.py:399` 后的 `OUTPUT_GROUP_PIPELINE` 分支：每个 AIC 先
   完成自己的全部 O_A 任务；然后按 g=0..7，仅对本核拥有的 O_B 组等待量化，
   调 `o_b_groups_stage`。**所有组结束后才统一 PHASE_OB（42）发布一次。**
2. `vector_schedule.py:915` 附近：每个 AIV 完成自己拥有的全部量化组，随后
   等 PHASE_OB 的 64 个列任务所覆盖的全部 24 AIC，再进入最终 helper。
   不是每个 AIV 都做八组量化；它按全局 `(g*ceil(T/32)+rowblock)%48` 领取。
3. `output_projection_b_stages.py:126` 的 NZ 数学中，
   `owner=(g*8+dc)%24`，dc=0..7，每个 dc 写 512 列且覆盖全部实际 M 行块。
   g0/3/6 对应 AIC0～7；g1/4/7 对应8～15；g2/5 对应16～23。
   因此任一 token 的完整4096列 partial 都依赖该组八个 AIC，不能仅等 token%24。
4. `o_dequant_hc_post_stage` 的输出 owner 为 `token%48`。每个 token 建
   `[1,4096]` FP32 acc，按 g=0..7 左折叠，当前内层 `pl.pipeline(...,stage=2)`
   将相邻两组 partial 的载入和转换交错。最后 HCpost 严格单行。

本文实际布局为 Native NZ2。ND 的 owner 还包含 `row_block`，不能直接照用
上述八核集合。若以后实现，ND 应保持旧路径，或独立证明它的生产/消费集合。

## 不能改变的数值链

每个 token、每一列独立保持：

```text
acc = FP32(+0)
for g = 0..7:
    acc = FP32_add(acc, FP32_mul(FP32_cast(partial_i32[t,g]), scale[g,t]))
projected_bf16 = BF16_rint(FP32_mul(acc, weight_scale))
x = FP32_cast(projected_bf16)
for out_h = 0..3:
    y = post[t,out_h] * x
    y = y + comb[t,0,out_h] * residual[t,0]
    y = y + comb[t,1,out_h] * residual[t,1]
    y = y + comb[t,2,out_h] * residual[t,2]
    y = y + comb[t,3,out_h] * residual[t,3]
    out[t,out_h] = BF16_rint(y)
```

不得换树归约、提前乘 weight scale、消除中间 BF16 舍入、先求残差总和，或对
多 token 使用同一 `scale[g,t0]` / post / comb。每组输出在 FP32 左折叠后仍须
保留 acc；在 g7 完成之前不能先做 HCpost。这里可重叠的是前七组归约工作，
不是把整个 HCpost 放到 O_B 未结束时执行。

## 两种真正不同的消费顺序

### A. 行外层：最小改动，但仅第一行获得流式机会

保持 `for t=worker,worker+48,...`，首行按 g=0..7 获取各组八个 owner 后，
载入该行 partial/scale 并做原加法；g7 后乘权重 scale、BF16 舍入、单行 HCpost。
后续行此时已经确认八组就绪，直接走原双缓冲归约，不再重复获取。

- 每核只需要原来一行 16 KiB accumulator，没有多 row 常驻或新增 GM partial。
- **每核第一行结束时八组已经全部就绪**，所以第二行及之后没有新的跨 O_B
  重叠机会。它们只整体提前了首行真正隐藏掉的工作，不是各行重复获得同等收益。
- 在保留整行4096列/原owner的条件下，T>48 时最多只有48行的前七组乘加能
  提前。下面的百分比是原八组归约项的数量占比，绝不是时间/性能上界。
- 不可机械地把等待放进每行：那会产生 `64*T` 次生产者获取。只首行获取为
  `64*min(T,48)`，当前整阶段等待是 `24*48=1152`（包括没有输出行的 AIV）。
  T≥48 时首行获取仍为3072次，是现状的2.67倍。具体每次是否立即命中以及
  fence/cache 代价没有本轮测量。
- 现有 stage=2 已经预读相邻组。不能只把通知等候写到 Python 循环中，任由
  lowering 将下一组 TLOAD 提前到该组获取之前。首行最保守可用顺序 range，
  或每两组都获取后再恢复成对预取；后者会减少可提前的部分，前者损失既有
  本地流水。二者均不能假设保持当前生成指令成本。

### B. 组外层：所有行受益，但 accumulator 跨组长期存活

保持每个 token 自己的 FP32 acc：`for g=0..7` 先获取该组，再遍历本 AIV
拥有的 token 行，分别读取各自行 scale，更新各自 acc。g7 后逐行原 BF16 舍入
和 HCpost。每行的加法次序与 A 相同；跨独立行换序本身不改变求和树。

1. **UB 保留**：每核至少 `ceil(T/48)*4096*4` 字节 accumulator；七档为
   16～64 KiB，另需 partial 的双缓冲、权重 scale、HCpost 四残差/临时值。
   g7 后处理第一行 HCpost 时，其余行 acc 还活着。不能按“结束归约后所有 acc
   都死亡”估计内存。Tile 的物理行数需要有界 constexpr 容量；可按 T 区间
   选择1/2/4行 bank并用实际T guard，不得用本次实际 B/S 静态展开或宣称无界支持。
2. **GM 保留**：若用 FP32 scratch[T,4096] 避免长期 UB，g0～6 各写一次，
   g1～7 各读一次，至少额外14份单行载荷，即 `14*T*4096*4` 字节。g0仍须保留
   原 `+0` 加法；不能为省一次载入悄悄改数学。scratch容量与原 partial/hidden
   不得重叠，同核顺序消费仍须正确完成自身 MTE3→MTE2 复用依赖。

| 场景 | T | 每 AIV 最多输出行 | UB acc 最低值 | A 可提前的归约项占比 | B 的 GM 方案额外载荷 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 128K B4 | 24 | 1 | 16 KiB | 87.50% | 5.25 MiB |
| 128K B8 | 48 | 1 | 16 KiB | 87.50% | 10.50 MiB |
| 128K B16 | 96 | 2 | 32 KiB | 43.75% | 21.00 MiB |
| 128K B24 | 144 | 3 | 48 KiB | 29.17% | 31.50 MiB |
| 128K B28 | 168 | 4 | 64 KiB | 25.00% | 36.75 MiB |
| 8K B16 | 96 | 2 | 32 KiB | 43.75% | 21.00 MiB |
| 8K B32 | 192 | 4 | 64 KiB | 21.875% | 42.00 MiB |

额外 GM 值是逻辑 payload，不是实测 HBM 流量；不考虑缓存命中，也不据带宽反推
时延。更没有把 UB 的最低值当完整内核的实际峰值。

## 组通知、phase 和无环合同

最直接且不滥用现有协议的做法是新增8个独立 OB_GROUP phase。每个 g 仅八个
实际 AIC writer 发布，合计64次；如果继续保留最后 PHASE_OB 供既有验证/兼容
路径使用，则是在原24次之外增加64次。不能用8×24个假发布掩盖实际 owner。
独立槽使 phase_count 60→68，当前512B隔离布局额外增加
`8*72*128*4=294912`字节（288 KiB），无需新增根Tensor，但信号区须按新合同
重新分配/清零并更新验证，旧工作区不能直接沿用。

不能在原 PHASE_OB 槽内用同一个 generation 发布八次：现有 `phase_sync.py`
明确是一次阶段完成，等待者可能把第一次当整阶段完成。改成组内进度计数属于
另一个协议设计，本文没有把它算成免费的替代方案。

在 AIV 仍完成自己全部量化、AIC 保持原组内数学/own-OA先行时，提前消费不存在
新的反向等待：OB只等quant，quant只等OA；最终反量化等待OB但不会阻塞尚未发布
的量化。八组 partial 各占独立 GM 区间且不复用，无逐槽 ACK 需求；这与 Score
双缓冲完全不同。若为扩大重叠又把 quant 和最终反量化交织，必须另查原组顺序
和发布先后，不能直接引用本次无反向依赖结论。

Scalar 非缓存一致性约束不变：AIC group写回后发布；AIV获取后才读 partial和
scale；保留业务流水完成/cache维护。单纯看到某组“时间上应该算完了”不是依据。
HF residual/post/comb保留至逐行HCpost完成，禁止用输出覆盖还没读完的输入。

## 现成UB证据和实际风险

保留既有真实生成文本片段 `existing_tail.cpp.txt`，来自上述旧诊断 AIV 的
`vector_schedule.cpp:60821` 起，不是新编译产物。局部常量按该函数作用域解析，
避免同文件其它函数复用 `v211` 等名字造成错误地址匹配。

- 权重 scale `[1,4096]` FP32在65536，acc在81920；partial两份槽为98304和114688，
  都是16KiB。生成代码确有两组 `TLOAD→TCVT→TMULS→TADD`，累加顺序保持g升序。
- BF16投影输入 HCpost 时先落本地98304，再转FP32复用81920；没有GM out_bf16。
- 四个FP32 residual的地址为98304、114688、0、16384，后继临时值继续复用。
  不能把这些不同生命周期对象简单相加，或者认为0～65536永远空闲。
- 在这个局部表达中，额外1～3行acc理论字节不是立刻超过UB，**未证明不可容纳**。
  但是多行bank跨group wait/循环活跃，g7 HCpost时还有其它行存活，可能改变整个
  fused kernel的reuse图。既有Attention local mi/li ring逻辑768B却导致整体
  Vec255104B超过当前188416B预算的失败，已经证明“局部字节很小”不足以保证通过。
  不能把那一失败外推成本方案也一定失败；这里只据此要求将整体规划作为前置门。

## 取舍与本次完成范围

暂不建议制作最小行外层候选：虽然它的UB风险小，但T96/144/168/192只覆盖
首行部分乘加，获取次数仍从1152增至3072，并可能打断原两组预取；新增64个AIC
发布又位于最终尾链。没有每组OB端点及归约自身耗时，当前无法判断它是否抵消。

也不建议为此直接做组外层GM累加：七档额外5.25～42MiB载荷、新scratch与依赖
成本已经明确，不能把它称为免费流水。组外层UB保留是更有意义的后备方向，
但需要1/2/4行有界bank、逐行scale与HCpost、真实dynamic T尾行、整体UB规划
和新的组通知合同；已经超出“只换一下等待位置”的最小改动。

如后续现成诊断能确认早期OB组完成后仍有足够AIV空窗，再考虑一个有界UB版，
而不是先扩大测试来碰运气。本次不安排额外诊断任务，也不声明这项数学机会关闭。
